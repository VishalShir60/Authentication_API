3. Core Architectural Decisions Explained

1. Separation of src/app.js and server.js

Why: If you start listening on a network port inside the file that configures Express, every integration test suite spinning up the app creates conflicting network port listeners. Separating them allows test runners like Supertest to import app and inject virtual HTTP requests directly in-memory without binding to a physical port.

2. Bcrypt with 10 Salt Rounds (Never Plain Hashes)

Why: Fast hash functions like MD5 or SHA-256 are dangerous for passwords because modern GPUs can compute billions of guesses per second. Bcrypt is an intentionally slow adaptive key derivation function. Its salt is randomly generated and prepended to the hash, completely nullifying precomputed Rainbow Table lookup attacks.

3. Generic Login Error Messages (Preventing User Enumeration)

Why: If an API returns "User not found" for a wrong email, and "Incorrect password" for a wrong password, an attacker can script requests to discover which emails belong to registered users. Returning the identical message "Invalid email or password" with HTTP 401 completely stops user enumeration.

4. Minimal JWT Payload (Only { id: user._id })

Why: JWT payloads are only Base64URL encoded—not encrypted. Anyone intercepting the token can decode and read its content. Keeping only the user ID prevents exposing confidential data and keeps the HTTP header lightweight on every single request.

4. High-Yield Interview Questions & Answers

Q1: What is the difference between Authentication and Authorization?
  • Authentication (AuthN): Verifying who the user is. (e.g., logging in with email and password to prove identity, resulting in an issued JWT).
  • Authorization (AuthZ): Verifying what permissions the authenticated user has. (e.g., checking if an authenticated user with ID 123 has permission to edit document 456 or access an admin panel).
Q2: Why do we hash passwords? Why use Bcrypt instead of SHA-256 or AES Encryption?
  • Why Hash: A hash is a one-way mathematical function. If the database is compromised, an attacker cannot reverse the hash back into the plain-text password.
  • Why not Encryption (AES): Encryption is two-way (reversible with a decryption key). Passwords should never need to be decrypted—only verified.
  • Why Bcrypt over SHA: SHA-256 is designed to be fast (for checksums). An attacker with a GPU can calculate 10+ billion SHA hashes per second. Bcrypt incorporates a cost factor (salt rounds) that forces CPU/memory work, drastically slowing down brute-force attacks to a crawl.
Q3: What is a JSON Web Token (JWT)? What are its three parts?
A JWT is a compact, URL-safe standard (RFC 7519) for transmitting claims securely. It has three parts separated by dots (header.payload.signature):
  1. Header: Specifies the algorithm (e.g., {"alg": "HS256", "typ": "JWT"}).
  2. Payload: Contains claims/data (e.g., {"id": "65b...", "exp": 1731...}).
  3. Signature: Created by taking the Base64 encoded Header and Payload, hashing them together with the server's private secret key: HMACSHA256(base64(header) + "." + base64(payload), secret). The server checks this signature to guarantee the client did not tamper with the payload.
Q4: Why keep the JWT payload small and add an expiration time?
  • Small Payload: The token travels in the Authorization header on every single HTTP request. A bloated token consumes bandwidth. Furthermore, JWT data is readable by anyone who decodes it—never store passwords, credit cards, or sensitive data inside it.
  • Expiration (expiresIn: '1d'): Since JWT is stateless, the backend does not look up active sessions in a database. If an attacker steals a token, they can impersonate the user until it expires. Short expiration limits this window of vulnerability.
Q5: How does Logout work with stateless JWTs, and what are its limitations?
  • How it works: In pure stateless authentication, logout is handled by the client application (e.g., frontend browser deletes the token from localStorage or cookies).
  • Limitation: The token remains cryptographically valid on the server until its expiration timestamp passes. If a token was intercepted, it can still be used.
  • Production Solution: Use a fast in-memory store like Redis to maintain a "token blacklist" (or store revoked Token IDs with a TTL matching the token's remaining lifetime).
Q6: What is Express Middleware? Walk through your authMiddleware.
Middleware is a function that sits between the incoming request and the final route handler, with access to (req, res, next). It can inspect, alter, or terminate the request.
Walkthrough of authMiddleware.js:
  1. Reads req.headers.authorization and checks if it starts with "Bearer ". Returns 401 Unauthorized if missing.
  2. Extracts the raw token string and verifies it with jwt.verify(token, process.env.JWT_SECRET).
  3. Queries MongoDB with User.findById(decoded.id).select('-password') to ensure the account still exists and password hash is never exposed in memory.
  4. Attaches the user object to req.user = user and calls next() so the downstream controller has access to the authenticated user.
Q7: How does Email Verification work in this project?
  1. On registration, the server generates a cryptographically secure 32-byte hex string using Node's native crypto.randomBytes(32).toString('hex').
  2. It saves this string into user.verificationToken with isVerified: false.
  3. Nodemailer sends a link (/api/auth/verify/:token).
  4. When clicked, the endpoint queries the database for a user matching the token, updates isVerified = true, and sets verificationToken = null to prevent token replay attacks.
  5. The login endpoint strictly blocks any user where isVerified === false with HTTP 403.
Q8: If you had more time, what would you add to scale this in production?
  1. Dual-Token Pattern (Access + Refresh Tokens): Issue a 15-minute Access Token stored in memory, and an HTTP-Only secure cookie containing a Refresh Token stored in the database with rotation to handle instant session revocation.
  2. Forgot/Reset Password Flow: Secure password reset using time-bounded (10-minute) hashed tokens sent via email.
  3. Role-Based Access Control (RBAC): Role middleware (e.g., authorizeRoles('admin', 'moderator')) to guard sensitive admin routes.
  4. Redis Token Blacklisting: Real-time session invalidation on logout.
